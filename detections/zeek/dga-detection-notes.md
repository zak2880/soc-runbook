# DGA Detection via Zeek DNS Logs — Rule 100107

**Date tuned:** 13 June 2026  
**Wazuh version:** 4.14.5  
**Rule file:** `/var/ossec/etc/rules/local_rules.xml`

---

## Rule 100107 Logic Summary

Rule 100107 fires on Zeek `dns.log` events (classified by parent rule 100106) where
the queried domain contains a label matching either of two DGA heuristics:

| Pattern | Description | Regex arm |
|---|---|---|
| Long alphanumeric label | Any single DNS label ≥ 26 chars (a–z, 0–9) | `(?:^|\.)[a-z0-9]{25,}[a-z0-9]\.` |
| Hex-only label | Any DNS label ≥ 16 characters using only hex digits (a–f, 0–9) | `(?:^|\.)[a-f0-9]{16,}\.` |

Both patterns are evaluated case-insensitively with PCRE2. The hex arm is what caught
the false positive below — Google Cast hardware IDs are 16-char hex strings.

---

## False Positive Pattern: mDNS / Chromecast / Google Cast

### Trigger

```
Source:      192.168.1.58 (LG TV / Google Cast device)
Destination: 224.0.0.251:5353 (mDNS IPv4 multicast)
Query:       cc4dd15b31306695._ghp._tcp.local
```

`cc4dd15b31306695` is a **static 16-char hex hardware ID** embedded in every Google
Cast device. It matches the hex arm of the DGA regex but is not generated by any DGA
algorithm — it is assigned at manufacture and never changes.

The `.local` TLD and destination `224.0.0.251:5353` are definitive indicators of
mDNS traffic. mDNS is a link-local protocol (RFC 6762); queries are multicast on the
LAN and **never forwarded to external resolvers**, making them categorically impossible
as DGA C2 infrastructure.

### Why it triggered

The rule had no awareness of mDNS. A hex hardware ID embedded as the first label of
an mDNS service name is visually indistinguishable from a DGA hex label to a naive
regex.

### Scope in this environment

Zeek DNS log audit (2026-06-13) found **18.1 million .local queries** (93% of all DNS
traffic), all legitimate, from:

| Device / Service | Top queries | Example |
|---|---|---|
| eWeLink smart home hub | 11.5M | `ewelink_100277e59f.local` |
| DNS-SD browsing | 3.8M | `_services._dns-sd._udp.local` |
| LG WebOS TV | 720K | `lgwebostv-el3n-3.local` |
| Google Cast / Nest | 600K+ | `_googlecast._tcp.local`, UUID-prefixed variants |
| Google Zone | 200K | `_googlezone._tcp.local` |
| Spotify Connect | 62K | `_spotify-connect._tcp.local` |
| Apple HomeKit (HAP) | 17K | `_hap._tcp.local` |
| Thread / Matter | ~28K | `_trel._udp.local`, `_matter._tcp.local` |

## Tuning Applied (2026-06-13)

### Base rule 100107 — hardened with negate exclusions

Three `negate="yes" type="pcre2"` conditions were added to rule 100107 so it will not
evaluate the DGA regex when the traffic is identifiably mDNS:

```xml
<!-- mDNS multicast destinations (IPv4 224.0.0.251 / IPv6 ff02::fb) -->
<field name="id.resp_h" type="pcre2" negate="yes">^(?:224\.0\.0\.251|ff02::fb)$</field>
<!-- mDNS port — all port 5353 traffic is local service discovery -->
<field name="id.resp_p" type="pcre2" negate="yes">^5353$</field>
<!-- .local TLD — mDNS names are LAN-only and cannot be DGA C2 domains -->
<field name="query" type="pcre2" negate="yes">\.local$</field>
```

> **Implementation note:** `type="pcre2"` is mandatory on `negate="yes"` field
> conditions. Without it, Wazuh uses OSSEC regex which does not honour `^`/`$`
> anchors, causing the negation to silently fail and the rule to fire anyway.

### Child suppression rules (belt-and-suspenders)

Four child rules with `if_sid: 100107` and `level: 0` were added. They act as a
safety net if rule 100107 somehow fires on mDNS traffic (e.g., after future regex
changes). A level-0 child rule overrides the parent alert.

| Rule ID | Match condition | Rationale |
|---|---|---|
| 100114 | `id.resp_h` = `224.0.0.251` | IPv4 mDNS multicast — never a C2 target |
| 100115 | `query` ends in `.local` | .local TLD is LAN-only by RFC 6762 |
| 100116 | `query` contains `_googlecast`, `_ghp`, `_tcp.`, or `_udp.` | mDNS service labels (Google Cast, Bonjour/DNS-SD) |
| 100117 | `id.resp_h` = `ff02::fb` | IPv6 mDNS multicast — never a C2 target |

> **Rule ID note:** IDs 100108–100111 were already taken by agent-health and ClamAV
> rules respectively. The suppression rules use 100114–100117.

## Wazuh-logtest Validation

### FP case (mDNS/Chromecast) — no alert expected

```json
{"ts":1781294154.046,"uid":"test123","id.orig_h":"192.168.1.58",
 "id.orig_p":5353,"id.resp_h":"224.0.0.251","id.resp_p":5353,
 "proto":"udp","trans_id":0,"query":"cc4dd15b31306695._ghp._tcp.local",
 "qtype":255,"qtype_name":"*","rcode":0,"rcode_name":"NOERROR",
 "AA":true,"TC":false,"RD":false,"RA":false}
```

**Result:** Rule 100106 fires (level 0, no alert). Rule 100107 suppressed by negate
conditions. ✓

### DGA case (external resolver) — level-8 alert expected

```json
{"ts":1781294200.000,"uid":"test456","id.orig_h":"192.168.1.100",
 "id.orig_p":54231,"id.resp_h":"8.8.8.8","id.resp_p":53,
 "proto":"udp","trans_id":1234,"query":"aabbccddeeff0011.c2beacon.example.com",
 "qtype":1,"qtype_name":"A","rcode":0,"rcode_name":"NOERROR",
 "AA":false,"TC":false,"RD":true,"RA":true}
```

**Result:** Rule 100107 fires at level 8. Alert generated. ✓  
MITRE: T1568.002 (DGA), T1071.004 (DNS C2)

> **Note on the original task test query:** `xk92mf3p.q7vbn1a.com` does not trigger
> rule 100107 because its labels (8 and 7 chars) are below both the 26-char and 16-hex-
> char thresholds. The corrected test above uses `aabbccddeeff0011` (16 pure hex chars)
> which matches the same arm of the regex that caught the Chromecast hardware ID.

## Deployment Notes

- **Container:** `single-node-wazuh.manager-1`
- **Host rules file:** `~/docker/wazuh/single-node/config/local_rules.xml`
- The docker-compose bind mount `./config/local_rules.xml → /var/ossec/etc/rules/local_rules.xml`
  is declared in `docker-compose.yml` but was not active in the running container (container
  predates the config entry). Changes must be applied with `docker cp` until the container
  is recreated from compose.
- After any rule change: `docker exec single-node-wazuh.manager-1 /var/ossec/bin/wazuh-control restart`
